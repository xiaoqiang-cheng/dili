# 界面文案与 i18n

## 现状

- 当前只有中文（`zh-CN`）。`shared/i18n.ts` 是唯一消息表入口，先做地基，不做一次性大改。
- 现有硬编码中文按区域逐步迁移：新增或改动某个面板时，把该面板的字符串移入消息表。当前已迁移用量、导出、运行诊断和公共按钮的文案；其余区域留待各自改动时处理。
- 不要为了“统一”一次性重写 `client/App.tsx` 的全部文案；那会制造巨大的无效 diff 和冲突。

## 用法

```ts
import { t, type MessageKey } from '../shared/i18n';

t('session.export')                    // 无参数
t('usage.input', { value: '1.2k' })    // 占位符
```

- 消息表是普通对象，`MessageKey` 由 `keyof typeof zh` 推导；拼错键会在类型检查时失败。
- 参数只做字符串替换，不做 HTML。需要富文本时拆成多段文案，不要传入标签。
- 新增语言 = 新增一份同键对象；缺键由类型检查发现，不允许运行时回退到中文却静默。
- 语言选择器、`<html lang>` 和日期格式属于后续工作；当前不要假装支持多语言。

## 迁移规则

1. 只迁移本次改动涉及的区域，保持 diff 可读。
2. 键名按区域分组：`session.*`、`group.*`、`usage.*`、`debug.*`、`common.*`。
3. 用户可见的错误信息也走消息表；服务端错误可以保留中文，客户端展示时再映射。
4. 测试：`shared/i18n.test.ts` 覆盖占位符、缺键和完整键集合。

## 不要做

- 不要引入 i18next/react-intl 等运行时依赖；当前需求是字符串表，不是格式化框架。
- 不要把后端返回的中文错误直接当键查表。
- 不要在 CSS 里写死带文案的 `content`。
