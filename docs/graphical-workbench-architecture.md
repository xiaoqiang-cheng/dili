# Dili 图形工作台架构改造方案

更新日期：2026-10-23。

## 产品目标

Dili 的图形界面最终应支持日常会话工作，不要求用户为正常输入、查看输出、审批、回答 Agent 问题、切换会话设置而打开原生终端。平台暂时不支持的操作必须在图形界面明确说明，并提供可靠的替代路径；不能把不支持的能力伪装成已支持。

Dili 统一联系人、群组、任务交接、消息呈现、草稿、发送状态和跨设备工作流。各 Agent 继续拥有其模型执行、身份认证、工具、权限策略和原生会话格式。优先调用 Agent 官方结构化接口、SDK 或 ACP；兼容 PTY/日志读取只作为有明确限制的后备路径。

## 架构目标

```text
联系人、群组、任务中心、远程工作台
                 |
统一图形交互：输入、消息、活动、审批、问题、设置
                 |
平台无关的会话和交互契约
                 |
Agent 适配器注册表
   |             |             |
Codex           Claude        Harness / ACP / 后续平台
                 |
官方 Agent 执行器、协议或受支持的原生界面
```

图形 UI 只消费公共事件和能力声明，不依据 Codex 专属数据类型判断消息行为。适配器负责原生身份、消息映射、执行控制和能力差异。新增平台应实现契约，而不需要修改所有 UI 组件。

## 交互契约

基础会话能力：发现、创建、恢复、Fork、读取分页历史。

对话能力：发送带幂等 ID 的文本和附件，订阅带修订号的增量事件，读取完整快照，停止当前轮，核对未知发送结果。

可选交互能力：回答审批、回答用户问题、读取和修改当前会话配置（模型、权限模式、推理等级等）、生成中补充输入、接入同一会话的原生终端。

适配器按运行时版本和会话执行模式报告能力状态：`supported`、`unsupported`、`experimental` 或 `native_required`，并提供原因。不得把平台名称等同于其所有安装版本的统一能力。

公共事件至少包含：消息新增／更新／完成、工具调用及结果、审批请求、用户问题、配置变化、回合状态、错误和历史截断。原生消息 ID、请求 ID、回合 ID 与来源事件 ID 必须保留，用于去重、重连对账和审计。

## 执行者与原生终端

每个会话同一时间只能有一个写入执行者。会话记录应能够表达执行模式（图形 Agent 协议、原生 PTY、原生 Web 或只读历史）、当前执行者身份和连接状态。图形执行器与 TUI 不得并行写入同一原生会话。

优先支持 Agent 明确提供的同实例交接。若协议只支持恢复持久会话 ID，不代表可以接入原运行进程。不能可靠交接时，产品应执行有确认的停止／暂停与恢复流程，或创建新的交接会话；不得声称两种模式控制同一个实时实例。

## 跨平台与模型交接

同一平台的原生会话内模型切换优先使用原生配置接口。若不支持，创建新的 Fork／交接联系人。

跨平台交接创建独立目标会话，来源会话保持不变。用户可审阅交接摘要、工作目录、相关消息和 Git 状态；界面显示已传递与未传递的上下文。默认不把整份超长对话隐式塞入目标上下文。

## 迁移步骤与完成门槛

### 阶段 0：基线与架构契约（进行中）

- 记录各 Agent 的版本、执行路径和能力差异。
- [x] 建立跨平台的聊天数据类型、`AgentChatAdapter` 契约与按 Backend 注册的适配器表；旧 `CodexChat*` 类型名保留为兼容别名。
- [ ] 为每个能力定义同一组适配器契约测试。
- 验收：现有 Codex、Claude 和 Harness 工作流不回归；接口定义不依赖 Codex 模块。

当前进度：公共聊天 API 已从 `CodexBridge` 类型解耦，并通过适配器表选择后端；当前只注册 Codex。Claude 原型仍未注册，Codex 外的执行语义未改变。下一步为接口建立共享契约测试，并梳理能力声明，之后才推进 Claude 的执行者交接。

### 阶段 1：Codex 作为结构化适配器基线

- 将现有 app-server 的流式消息、历史、审批、问题、停止和设置能力映射到公共契约。
- 将公共聊天 API 和 UI 从 Codex 专属名称改为 Agent 通用命名，保留现有 HTTP 路径兼容。
- 补充断线、服务重启、事件重复和未知发送结果的统一恢复测试。
- 验收：输入只出现一条；流式消息在重连后不丢不重；审批和提问可在图形界面完成。

### 阶段 2：Claude 图形执行路径验证与接入

- 评估现有 `ClaudeChatBridge` 的官方协议兼容、流式、工具、审批、问题和配置覆盖。
- 明确图形执行器与交互式 TUI 的身份关系；实现单写入者约束与可恢复交接。
- 不把尚未验证的 stream-json 执行路径与 TUI 宣称为同一实时实例。
- 验收：新会话和已导入会话的创建／恢复、中文输入、附件、流式回复、工具审批、用户问题、模型／权限设置和恢复路径均有真实 CLI 版本记录。

### 阶段 3：Harness 与 ACP

- 优先使用 Harness 已公开的会话 API 或其原生 Web UI 能力。
- 探测 ACP 的初始化、会话恢复、配置选项、附件及权限交互；逐项映射，缺少的能力如实报告。
- 验收：适配器契约测试通过，并记录可支持的版本范围和原生入口。

### 阶段 4：新增平台扩展机制

- 先用内置适配器验证扩展点，再定义外部适配器清单、权限边界、升级策略和兼容版本。
- 外部适配器具有进程执行、文件访问和会话控制权限，未设计隔离与信任模型前不启用任意动态插件。
- 验收：新增一个平台不需修改通用聊天组件、会话状态机或已有适配器。

## 适配器契约测试

每个适配器必须明确验证：创建和恢复、Unicode／多行发送、附件声明、流式及历史一致性、重复事件去重、审批与问题回答、停止、模型／权限设置、结果不确定时禁止盲目重试、网络断开恢复、服务重启恢复，以及图形与原生模式交接。无法支持的能力应有显式负向测试。

自动化测试使用隔离 CLI fixture；发布前另记录真实 CLI 版本和真实会话验收。模拟协议通过不能替代真实 Agent 兼容性验证。

## 当前代码与首批改造

- `server/codex.ts`：现有 app-server 客户端及 Codex 执行能力。
- `server/chat-api.ts`：通过 `registerAgentChat` 使用 `AgentChatAdapter` 和按 Backend 注册的适配器表；HTTP 路由保持兼容。
- `server/agents/chat.ts`：平台无关的聊天适配器契约与注册表。
- `shared/chat.ts`：定义 `AgentChat*` 平台无关类型，同时保留 `CodexChat*` 兼容别名。
- `server/claude-chat.ts`：独立结构化协议原型，当前未由 `server/index.ts` 主流程启动；在完成执行者和交接审查前不直接接入生产路由。
- `server/dsh.ts`：Harness 会话及原生 Web 集成；图形聊天采用独立适配方案评估。
- `client/CodexChatPane.tsx`：成熟的图形交互面板，后续重命名并让其仅消费公共聊天契约。

## 版本与发布

每个阶段先更新本文件和 `TODO.md`，再实现并执行 `npm run check`、相关服务端测试和隔离浏览器测试。阶段边界清晰时创建本地提交，描述可验证的用户行为。未经明确授权不 push、不建 tag、不重启承载当前会话的服务。
